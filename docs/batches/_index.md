# 작업 묶음

> 한 대화(세션)에서 퍼블할 화면들을 묶고 순서와 먼저 끝나야 할 것을 정한다. 화면이 많으면 한 번에 끝낼 수 없어서, "이번에 무엇을 어떤 순서로 할지"를 남겨 두기 위해서다.
> 묶음은 `plan-batch` 스킬로 만든다. 양식: `templates/batch.md`. 파일: `docs/batches/<번호>-<이름>.md` (예: `03-account-list.md`)
> 아래 "현황"과 각 묶음 파일의 "현황"은 `build-index` 훅이 자동 생성한다. 직접 고치지 않는다.
> IMPORTANT: 현황은 전체를 읽지 말고 필요한 묶음 행만 검색한다. (토큰 절감)

## 1. 묶음이 다루는 것
- 퍼블과 다시 퍼블(버전 변경·질문 확정으로 고친 화면)만 다룬다. 명세 작성은 묶지 않는다.
- 대상은 명세 상태가 "확정"인 화면, 그리고 명세를 고쳐 다시 "확정"이 된 "다시 퍼블" 화면이다. "수정필요" 화면은 명세를 고쳐 확정한 뒤에 넣는다. (`docs/changes/_index.md` 3번)
- 화면 상태와 검수 결과는 묶음 파일에 적지 않는다. 원본은 화면 명세 frontmatter와 보고 파일이고, 묶음 파일에는 현황으로 자동 표시된다.

## 2. 묶는 기준
1. IA에 WBS 일정이 있으면 같은 기간에 퍼블 예정인 화면을 모으고, 그 안에서 도메인·패턴으로 나눈다. (예정일은 `docs/ui-flow/_index.md` 화면 맵의 "예정일" 칸)
2. WBS가 없으면 도메인 안에서 패턴 순서로 묶는다. (패턴은 플로우 "2. 화면 목록" 표의 "패턴" 칸)
3. 다시 퍼블할 화면은 새 퍼블과 섞지 않고 따로 묶는다. 같은 변경 기록(`docs/changes/`)에서 나온 화면끼리 묶는다.
4. 한 묶음은 기본 5화면까지 (5번 예외에서 바꾼다). 넘으면 나눈다.
5. 한 화면은 열린 묶음 하나에만 넣는다. (완료된 묶음의 화면을 다시 퍼블하면 새 묶음에 넣는다)

## 3. 순서 정하는 법
| 순서 | 무엇 | 이유 |
|---|---|---|
| 1 | 아직 없는 공통 컴포넌트 (컴포넌트 명세 → 구현) | 화면이 조립만 하도록 |
| 2 | 이동해 가는 공통 화면 (`docs/ui-flow/_index.md` "공통 화면") | 다른 화면의 `data-screen-link` 대상 |
| 3 | 같은 패턴 화면끼리 이어서 | 앞 화면의 구성을 다음 화면이 재사용 |
| 4 | 플로우 순서 (목록 → 상세, 입력 → 확인 → 결과) | 앞 화면의 더미 데이터·필드 이름을 이어서 쓴다 |

## 4. 작업 방식
- **묶음 하나 = 대화 하나.** 화면 하나를 마치면 보고 파일을 저장하고 `/compact`로 맥락을 정리한다. 다음 화면은 묶음 파일과 그 화면 명세만 읽고 시작한다. (`docs/HARNESS.md` 4번)
- **묶음 하나 = 브랜치 하나 = PR 하나.** 화면마다 커밋하고 보고 파일을 남긴다. (`docs/GIT.md` 1번)
- 선행 조건(묶음 파일 3번)을 만족하지 못하면 시작하지 않는다. 아직 없는 공통 컴포넌트는 묶음의 첫 순서로 넣어 먼저 만든다.
- 진행 중에 순서·대상을 바꾸려면 묶음 파일 2번 표를 고치고 승인받는다.
- **완료**: 대상 화면이 모두 "구현완료"이고 검수 결과가 "통과" 또는 승인받은 "조건부 통과"면 현황에 "완료"로 표시된다. (`docs/QA.md` 4번)
