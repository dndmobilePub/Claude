# ARCHITECTURE.md — 코드 구조 규칙

> 화면·라우트·데이터·상태 코드를 어디에 어떻게 두는지 정한다. 공통 규칙과 이유만 담는다.
> 실제 경로는 맨 아래 예외 섹션, 라이브러리 이름은 `docs/PROJECT.md` 기술 스택을 따른다.
> 컴포넌트 폴더 규칙은 `src/components/CLAUDE.md`, 디자인 값 규칙은 `docs/DESIGN.md`를 따른다.

## 1. 계층과 책임
| 계층 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 라우트 | URL과 화면 연결, 접근 조건(로그인·인증) 지정 | 화면 내용, 데이터 호출 |
| 화면 | 컴포넌트 조립, 데이터 계층 호출, 화면 상태 처리 | 디자인 값, 서버 직접 호출, 금액·마스킹 직접 구현 |
| 컴포넌트 | `src/components/CLAUDE.md` 참조 | 데이터 호출 |
| 데이터 | 서버 호출, 응답 타입 정의, 임시 데이터 반환 | UI, 라우팅 |
| 공통 | 금액·마스킹 포맷, 날짜, 검증 같은 유틸 | 화면별 업무 규칙 |

- 가져오는 방향은 한쪽만: 라우트 → 화면 → 컴포넌트·데이터·공통. 데이터·공통은 화면을 가져오지 않는다.
- IMPORTANT: 화면끼리 서로 가져오지 않는다. 여러 화면이 쓰는 것은 조합 컴포넌트나 공통으로 옮긴다.

## 2. 기본 폴더 구조
```
src/
  screens/<도메인>/<화면ID>-<이름>/   # 화면 (3번)
  components/                       # 컴포넌트
  api/<도메인>.ts                    # 데이터 계층 함수 (5번)
  api/types/<도메인>.ts              # 응답 타입
  mocks/<도메인>.ts                  # 임시 데이터 (6번)
  stores/                           # 플로우·전역 상태 (7번)
  lib/                              # 공통 유틸
  styles/                           # 토큰
```
- 라우트 위치는 스택마다 다르다. (9번)
- `<도메인>` 폴더 이름은 플로우 문서 파일 이름과 같게 한다. (예: `ui-flow/transfer.md` → `screens/transfer/`)

## 3. 화면 폴더
- 폴더 이름: `<화면ID>-<PascalCase 이름>` (예: `TRF-010-AmountInput`). 화면 ID로 바로 찾을 수 있게 한다.
- 화면 컴포넌트 이름: `<이름>Screen`. 프로젝트 전체에서 겹치지 않게 도메인을 붙인다. (예: `TransferResultScreen`)
- 폴더 안: 화면 본체(index), 화면 전용 조각, 화면 전용 훅(`useXxx`). 스타일 파일은 스타일링 방식을 따른다.
- 화면 전용 조각이 두 화면 이상에서 쓰이면 조합 컴포넌트로 옮긴다.

## 4. 라우트
- 라우트 파일은 화면 컴포넌트를 가져와 렌더링만 한다. 화면 코드를 라우트 파일에 쓰지 않는다.
- URL은 의미 있는 영문 소문자·하이픈으로 쓴다. (예: `/transfer/amount`) 화면 ID는 URL에 넣지 않는다.
- 화면별 URL의 원본은 화면 명세 frontmatter의 `route`다.
- 로그인·인증 같은 접근 조건은 라우트에서 공통으로 처리한다. 화면마다 따로 확인하지 않는다.
- IMPORTANT: 개인정보·금액·인증 정보를 URL 파라미터로 넘기지 않는다. (`finance-ui.md` 4번) 화면 사이 데이터는 플로우 상태(7번)로 넘긴다.

## 5. 데이터 계층
- IMPORTANT: 화면은 `api/<도메인>`의 함수만 호출한다. 화면·컴포넌트에서 fetch·HTTP 클라이언트를 직접 쓰지 않는다.
- 함수 하나 = 엔드포인트 하나. 이름은 동사+대상. (예: `getAccounts`, `requestTransfer`)
- 응답 타입은 `api/types/<도메인>.ts`에 둔다. API 명세가 나오기 전에는 화면 명세 5번의 필요 필드로 먼저 정의한다.
- 에러는 공통 에러 형식(문의용 코드 + 사용자 안내 문구)으로 바꿔 넘긴다. 서버 메시지를 그대로 화면에 넘기지 않는다.
- 세션 만료·점검 응답은 공통으로 처리한다. 화면마다 처리하지 않는다. (`finance-ui.md` 7·8번)
- 금액은 서버 값을 그대로 쓰고 화면에서 계산하지 않는다. (`finance-ui.md` 1번)

## 6. 임시 데이터 (API 확정 전)
- IMPORTANT: 임시 데이터는 데이터 계층 함수 안에서만 반환한다. 화면·컴포넌트에 고정 데이터를 쓰지 않는다.
  → API가 나오면 그 함수 본문만 바꾸고 화면 코드는 고치지 않기 위해서다.
- 값은 `mocks/<도메인>.ts`에 두고, 타입은 5번의 응답 타입을 그대로 쓴다.
- 임시 처리한 함수에는 `TODO(<화면ID>): API 확정 시 교체` 주석을 단다.
- 로딩·빈 값·에러 상태를 확인할 수 있게 지연과 시나리오(정상/빈 값/에러)를 바꿀 수 있게 만든다.
- 실제 개인정보·계좌번호를 쓰지 않는다. 가짜임이 드러나는 값을 쓴다.
- 배포 전에 `TODO(` 검색으로 남은 임시 데이터가 없는지 확인한다.

## 7. 상태 관리
- 가까운 곳부터 쓴다: 컴포넌트 지역 상태 → 화면 상태 → 플로우 상태 → 전역 상태.
- 플로우 상태: 여러 화면에 걸친 입력값. (예: 이체 금액 → 확인 화면) 플로우가 끝나거나 이탈하면 지운다.
- 전역 상태: 로그인 사용자 정보처럼 앱 전체가 쓰는 것만 둔다.
- 서버에서 받은 데이터를 전역 상태에 복사해 두지 않는다.
- IMPORTANT: 민감 정보를 브라우저 저장소(localStorage·sessionStorage)에 두지 않는다. (`finance-ui.md` 4번)

## 8. 폼·입력 검증
- 검증 규칙의 원본은 화면 명세 6번이다. 규칙은 화면별 검증 스키마 한 곳에 모으고, 입력 컴포넌트마다 흩어 쓰지 않는다.
- 에러 문구는 화면 명세에 적힌 문구를 그대로 쓴다. 없으면 지어내지 않고 묻는다.

## 9. 스택별 예시
### React + Vite (React Router)
```
src/routes/index.tsx                          # 라우트 정의
src/screens/transfer/TRF-010-AmountInput/index.tsx
```

### Next.js (App Router)
```
app/transfer/amount/page.tsx                  # 화면 컴포넌트 렌더링만
src/screens/transfer/TRF-010-AmountInput/index.tsx
```
- Next.js에서도 화면은 `app/` 안에 두지 않는다. 라우트와 화면을 나눠야 2번 구조와 규칙 적용 경로(`src/`)가 스택과 상관없이 같다.
