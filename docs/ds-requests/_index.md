# 디자인 시스템 변경 요청

> 디자인 시스템(Figma 라이브러리·변수)에 없는 것이 필요할 때 디자이너에게 추가·변경을 요청하고, 결정과 후속 작업을 추적한다.
> 요청 하나 = 파일 하나: `docs/ds-requests/<요청 ID>-<짧은 이름>.md` (예: `DS-003-amount-chip.md`). 양식: `templates/ds-request.md`
> 아래 "현황"은 `build-index` 훅이 자동 생성한다. 직접 고치지 않는다.
> IMPORTANT: 현황은 전체를 읽지 말고 필요한 요청 ID·화면 ID 행만 검색한다. (토큰 절감)

## 1. 질문·요청·ADR 구분
| 무엇 | 언제 | 끝나는 때 | 위치 |
|---|---|---|---|
| 질문 | Figma 디자인이 무엇을 뜻하는지 확인 (상태 디자인이 있는지, 프레임 폭이 왜 다른지, 화면끼리 왜 다른지) | 답을 받으면 | `docs/questions/design.md` |
| DS 변경 요청 | 디자인 시스템에 추가·변경이 필요함 (토큰·컴포넌트·변형·아이콘이 없거나, 직접 그린 요소를 컴포넌트로 만들어야 함) | 반영 / 대체 / 기각이 정해지면 | 이 폴더 |
| ADR | 우리 쪽 구조·규칙 결정 (여러 화면에 영향, 규칙의 예외) | 승인되면 | `docs/decisions/` |

- 질문을 하다가 디자인 시스템 변경이 필요하다는 답이 나오면, 질문은 답으로 닫고 요청을 새로 만든다. 질문 답 칸에 요청 ID를 적는다.
- "기존 요소로 대체"하기로 한 결정도 이 폴더의 요청 파일에 남긴다. ADR을 따로 쓰지 않는다.

## 2. 상태
| 상태 | 뜻 | 다음 |
|---|---|---|
| 요청 | 요청 파일을 만듦 | 디자이너에게 전달 |
| 디자이너 검토 | 디자이너가 보고 있음 | 결정을 받음 |
| 반영 | Figma 라이브러리·변수에 추가·변경됨 | 요청 파일 5번 후속 작업 |
| 대체 | 기존 요소로 하기로 함 (무엇으로 대체하는지 4번에 적음) | 관련 화면 명세에 반영 |
| 기각 | 필요 없다고 결정됨 | 관련 화면 명세에 반영 |

- "요청"·"디자이너 검토"는 **열린 요청**이다. 열린 요청의 `screens`에 있는 화면은 명세 확정·퍼블·작업 묶음을 시작하지 않는다.
- 결정은 사용자나 디자이너에게서 받는다. AI가 정하지 않는다.
- 파일은 지우지 않는다. 상태와 4번 결정만 바꾼다.

## 3. 반영 뒤 후속 작업
- 토큰·변수가 바뀌면 `token-sync`
- 컴포넌트·변형이 생기면 컴포넌트 명세(`templates/component-spec.md`, `figma_name` 연결) → 구현
- 관련 화면 명세의 2번 구성·3번 상태를 고친다. 확정·구현완료였던 화면은 디자인 버전 변경으로 처리할지 묻는다. (`version-update`)
