# 작업 묶음 만들기

> 규칙 원본: `docs/batches/_index.md` (다루는 것, 묶는 기준, 순서, 작업 방식). 양식: `templates/batch.md`
> 이 스킬은 묶음을 **제안하고 저장**만 한다. 퍼블은 `implement-screen <묶음 ID>`로 한다.

## 입력
- 기본: 묶음 밖 퍼블 대상 전체에서 다음 묶음 하나를 제안한다.
- 범위를 지정받으면 그 안에서만 (예: 도메인 키, WBS 기간, 변경 기록 파일)

## 원칙
- 화면 목록·상태는 다시 판단하지 않는다. 현황 표(자동 생성)에서 검색해 쓴다. 표 전체를 읽지 않는다.
- 명세가 "확정"이 아닌 화면은 넣지 않는다. 명세 작성이 먼저다.
- 묶음 파일에 화면 상태·검수 결과를 적지 않는다.
- 저장 전에 초안을 보여주고 승인받는다.

## 멈춤 조건 (해당하면 즉시 멈추고 묻는다)
- 묶음 밖 퍼블 대상이 없음 → 명세 작성(`write-screen-spec`)이 먼저라고 안내한다
- 코드 토큰 파일이 없음 → `token-sync`를 먼저 안내한다
- 후보 화면의 플로우에 패턴 칸이 비어 있음 → `write-flow`로 채울지 묻는다 (순서를 정할 수 없다)

## 단계

### 1. 후보 찾기
- `docs/batches/_index.md` 현황의 "묶음 밖 퍼블 대상" 목록을 본다.
- 다시 퍼블 후보: 그 목록 중 `docs/reports/<화면ID>.md`가 이미 있는 화면. 어떤 변경 때문인지 `docs/changes/`에서 화면 ID로 검색한다.
- 후보마다 아래만 검색해 모은다.
  - `docs/ui-flow/_index.md` 화면 맵의 그 화면 행: 도메인, 예정일, 열린 질문 수
  - 플로우 "2. 화면 목록" 표의 그 화면 행: 패턴

### 2. 묶기 (`_index.md` 2번)
- WBS 예정일이 있으면 가장 이른 기간의 화면부터 모으고, 그 안에서 도메인·패턴으로 나눈다.
- 없으면 한 도메인 안에서 패턴 순서로 모은다.
- 다시 퍼블 화면은 새 퍼블과 섞지 않는다. 같은 변경 기록에서 나온 화면끼리 묶는다.
- 크기 기준(기본 5화면, `_index.md` 5번 예외)을 넘으면 나눈다.
- 열린 차단 질문이 있는 화면은 빼고, 뺀 이유를 보고한다.

### 3. 선행 조건 확인 (양식 3번)
- 대상 화면 명세에서 2번 구성의 "신규"·"확장" 컴포넌트와 4번 이동 화면만 검색한다.
- 필요한 공통 컴포넌트가 아직 없으면(`docs/components/_index.md`에서 상태가 "구현완료"가 아님) 2번 표 앞 순서에 화면 ID 칸 `컴포넌트: <이름>`, 작업 칸 "컴포넌트"로 넣는다.
- 이동해 가는 공통 화면이 아직 퍼블 전이면 비고에 적는다. (`data-screen-link` 표시는 할 수 있으므로 막지 않는다)

### 4. 순서 정하기 (`_index.md` 3번)
공통 컴포넌트 → 공통 화면 → 같은 패턴끼리 → 플로우 순서.

### 5. 초안 → 승인 → 저장
- 양식대로 초안을 보여준다. 다음 번호와 이름(도메인·패턴을 담은 영문 소문자)을 제안한다.
- 승인 후 `docs/batches/<묶음 ID>.md`로 저장한다. 템플릿 주석은 지운다.
- 저장하면 `build-index` 훅이 현황을 만든다. 경고(열린 묶음 두 곳에 같은 화면, 화면 목록에 없는 ID)가 나오면 보고한다.
- 커밋은 묶음 퍼블 브랜치의 첫 커밋으로 한다. (`docs/GIT.md`, 메시지 `docs(batch): <묶음 ID> 작업 묶음`)

## 보고 형식
```
## 작업 묶음 제안: <묶음 ID>
- 근거: (WBS 기간 / 도메인 / 패턴 / 변경 기록)
- 대상: 화면 n (퍼블 n · 다시 퍼블 n) + 선행 컴포넌트 n
- 뺀 화면: (화면 ID와 이유 — 차단 질문 등)
- 남은 묶음 밖 대상: n
```
