# 화면 퍼블 절차

> 규칙 원본: `docs/DESIGN.md`, `docs/ARCHITECTURE.md`(퍼블 파일 구조·퍼블과 개발의 경계), `docs/QA.md`(검수 기준·결과), `.claude/rules/` (figma-design-system · a11y · finance-ui).
> 이 스킬은 규칙을 반복하지 않고 **작업 순서와 멈춤 지점**만 정한다.

## 입력
- 화면 ID (예: ACC-010) 또는 작업 묶음 ID (예: 03-account-list)
- 화면 하나씩 1~8단계를 끝낸다. 여러 화면을 섞어 진행하지 않는다.

## 묶음으로 진행할 때 (`docs/batches/_index.md` 4번)
- 묶음 파일을 읽고 3번 "먼저 끝나야 할 것"을 확인한다. 하나라도 안 되면 시작하지 않고 보고한다.
- 묶음 하나 = 브랜치 하나: `feat/batch-<묶음 ID>`. 첫 커밋은 묶음 파일이다. (`docs/GIT.md`)
- 2번 표 순서대로 진행한다. "컴포넌트" 줄은 `templates/component-spec.md`로 명세 → 승인 → 구현한다. 화면 줄은 아래 1~8단계를 그대로 한다.
- 화면 하나를 마치면(8단계 커밋 후) 다음 화면으로 넘어가기 전에 `/compact`로 맥락을 정리하자고 안내한다. 다음 화면은 묶음 파일과 그 화면 명세만 읽고 시작한다.
- 순서·대상을 바꿔야 하면 묶음 파일 2번 표를 고치고 승인받는다.
- 마지막 화면을 마치면 묶음 현황(자동)으로 완료를 확인하고 PR 생성을 제안한다. PR 본문은 화면별 보고 파일 링크와 결과 목록이다.

## 멈춤 조건 (해당하면 즉시 멈추고 묻는다)
- 화면 명세 파일이 없거나 Figma 노드 URL이 비어 있음
- 화면 상태가 "확정"이 아님 (`write-screen-spec`의 확정 점검을 먼저 안내. "수정필요"면 명세 수정부터)
- 이 작업에 필요한 `docs/PROJECT.md` 값(뷰포트·퍼블 언어·TypeScript·스타일링·토큰 위치·명령어)이 [TODO]
- `docs/ARCHITECTURE.md` 11번 예외의 "화면 하나를 따로 여는 방법"·"상태를 바꿔 보는 방법"이 [TODO]
- 코드 토큰 파일이 없거나, 필요한 Figma 변수가 토큰 파일에 없음 (`token-sync`를 먼저 안내)
- Figma 값에 대응하는 토큰·컴포넌트가 없음 (DESIGN.md 8번 절차)
- 필요한 상태(로딩·빈 값·에러 등)의 디자인이 Figma에 없음
- 명세 4번에 담당(퍼블/개발)이 비어 있는 동작이 있음
- 대상이 이 화면 ID이고 차단 "예"인 질문이 열려 있음 (`docs/questions/`)
- 이 화면이 "멈춘 화면"인 열린 DS 변경 요청이 있음 (`docs/ds-requests/`)
- Figma 컴포넌트 인스턴스 중 연결 목록에 없고 명세 2번에 "신규"로도 없는 것이 있음 (`DESIGN.md` 4번)

## 단계

### 1. 사전 점검
- `docs/screens/<화면ID>.md`를 읽는다. 연결된 플로우 문서는 해당 섹션만 읽는다.
- 다른 화면 명세는 읽지 않는다. (토큰 절감)
- `docs/ARCHITECTURE.md`는 이 화면에 필요한 섹션만 읽는다. (보통 1번, 3번 중 `docs/PROJECT.md` "파일 구조"에 맞는 절, 4~8번, 9번의 해당 언어)
- 같은 도메인의 기존 화면(화면 폴더 `screens/<도메인>/`, 종류별 폴더 `html/<도메인>/`)과 더미 데이터(`dummy/<도메인>`)가 있는지 확인한다. 있으면 그 방식을 따른다.
- `docs/questions/`에서 이 화면 ID가 대상인 열린 질문(미답변·보류·가정)만 검색한다. 가정 값은 명세의 `가정(Q-ID)` 표시대로 쓴다.
- 이미 퍼블한 화면을 버전 변경 때문에 다시 퍼블하는 경우: `docs/changes/`에서 대상이 이 화면 ID인 줄만 검색해 무엇이 바뀌었는지 확인하고, 계획(3단계)에 바뀐 부분만 담는다. 커밋 메시지 끝에 `(<원본> <버전> 반영)`을 붙인다.
- 멈춤 조건을 확인한다.

### 2. Figma 조회
- `figma-design-system.md` 1번 절차대로 명세의 노드만 조회한다.
- 필요할 때만 `get_variable_defs`, `get_code_connect_map`을 추가로 호출한다.

### 3. 퍼블 계획 제시 → 승인
아래 내용을 보여주고 승인을 받기 전에는 파일을 만들거나 고치지 않는다.
- 요소 매핑표

  | Figma 요소 | 사용할 컴포넌트 | 구분 (기존 / 확장 / 신규) |
  |---|---|---|

- 대응 토큰이 없는 값 목록
- 만들거나 고칠 파일 목록 (`ARCHITECTURE.md` 3·9번 경로 기준: 화면 파일, 더미 데이터, 공통 유틸. 화면 전용 스타일 파일은 없다)
- `global.css` 예외가 필요하면 그 이유와 먼저 검토한 방법(컴포넌트 변형·공통 스타일). 없으면 "없음" (`ARCHITECTURE.md` 8-1)
- 구현할 상태 목록과 "디자인 필요" 항목
- 퍼블에서 구현할 동작과 개발에 넘길 동작 (명세 4번 담당 기준)

### 4. 신규 컴포넌트 (필요할 때만)
- `templates/component-spec.md`로 명세를 먼저 쓰고 승인받은 뒤 만든다.

### 5. 퍼블
- 승인된 계획 범위 안에서만 작업한다. 범위가 바뀌면 다시 승인받는다.
- 작업 중 새 질문이 생기면 지어내지 않고 멈춰 묻는다. 답이 없으면 `docs/questions/_index.md` 규칙대로 남긴다.
- 화면 파일은 조립만 하고 디자인 값을 직접 쓰지 않는다. 스타일은 컴포넌트·공통에서 해결하고, 승인된 예외만 `global.css`에 `ARCHITECTURE.md` 8-1 형식으로 넣는다.
- 화면 폭은 `DESIGN.md` 6-2를 따른다. 가로 폭만 유동이고 디자인 프레임 폭을 width 고정값으로 쓰지 않는다.
- 명세에 적힌 상태를 모두 만들고, `ARCHITECTURE.md` 6번 방법으로 바꿔 볼 수 있게 한다.
- 명세 4번 "퍼블" 담당 동작만 구현한다. 화면 사이 이동은 구현하지 않고 `data-screen-link`로 표시한다. (`ARCHITECTURE.md` 4번)
- 더미 데이터는 명세 5번 필드 이름으로 `ARCHITECTURE.md` 5번 방식대로 넣는다.
- 공통 유틸(`lib/`)을 만들거나 고치면 단위 테스트를 함께 만든다. (`ARCHITECTURE.md` 3번, 업종별 필수 항목은 `.claude/rules/`)

### 6. 검증
`docs/QA.md` 1번 순서대로 한다. 결과는 대화에 길게 쓰지 않고 8단계 보고 파일에 모은다.
1. `docs/PROJECT.md`의 린트/테스트 명령을 실행한다. ("없음"이면 건너뛰고 기록한다)
2. `ds-check` 스킬로 디자인 시스템 위반을 점검한다.
3. 시각 비교: 명세 3번 상태마다 디자인 프레임 폭에서 Figma `get_screenshot`과 퍼블 화면 캡처를 비교한다. 허용 차이·원인 분류는 `QA.md` 3번을 따른다.
4. 구현 기준 폭과 최소 폭으로 열어 가로 스크롤·겹침·의도하지 않은 줄바꿈이 없는지 확인한다. (`DESIGN.md` 6-2)
5. 상태별로 화면을 바꿔 가며 확인한다.
6. 규모가 크거나 신규 컴포넌트가 있으면 `design-system-reviewer` 에이전트에 독립 검토를 맡긴다. 화면 ID, 바뀐 파일 목록, ds-check 결과, 개발 전달 목록·가정 목록 초안을 함께 넘긴다.
- "구현 오류"·"토큰·컴포넌트 차이"는 고친 뒤 그 단계부터 다시 검증한다.
- 다시 퍼블한 화면(버전 변경·질문 확정)은 `QA.md` 5번 범위만 다시 비교한다.

### 7. 체크리스트 대조
- `QA.md` 2번 공통 체크리스트와 화면 명세 9번 화면별 기준을 항목별로 확인한다. 확인하지 못한 항목은 이유를 적는다.
- `QA.md` 4번으로 결과(통과 / 조건부 통과 / 미통과)를 정한다.

### 8. 보고 → 승인 후 마무리
- `templates/report.md` 양식으로 `docs/reports/<화면ID>.md`를 만든다(있으면 통째로 덮어쓴다). 기준 버전 칸은 명세 frontmatter와 같게 적는다.
- 대화에는 아래 "완료 보고 형식"의 요약만 보여주고 승인을 받는다.
- 결과가 "미통과"면 상태를 바꾸지 않는다. 고칠 범위를 보고하고 6단계로 돌아간다.
- 승인을 받은 뒤:
  - 보고 파일을 저장한다.
  - 화면 명세 frontmatter의 `status`를 "구현완료"로, `updated`를 오늘 날짜로 바꾼다. 이번에 만든·확장한 컴포넌트 명세의 `status`도 "구현완료"로 바꾼다.
  - `_index.md`는 고치지 않는다. (`build-index` 훅이 자동 갱신)
  - `docs/GIT.md` 규칙대로 작업 브랜치에 커밋한다. 메시지 형식: `feat(<화면ID>): <화면명> 퍼블`. 보고 파일은 퍼블과 같은 커밋에 넣는다.
  - 화면 하나만 진행했으면 PR 생성을 제안한다. (생성은 승인 후, `.github/pull_request_template.md` 양식. 본문은 보고 파일 링크와 요약) 묶음이면 묶음의 마지막 화면 뒤에 한 번만 제안한다.

## 완료 보고 형식
대화에 보여주는 요약이다. 자세한 내용은 보고 파일에 있다.
```
## <화면ID> <화면명> 퍼블 결과 — [통과 / 조건부 통과 / 미통과]
- 보고 파일: docs/reports/<화면ID>.md
- 검증: 린트·테스트 [통과/실패/없음] · ds-check [위반 n건] · 시각 비교 [차이 n건: 원인 분류별 개수] · 기준 폭·최소 폭 [문제 없음/내용]
- 체크리스트: 공통 n/n · 화면별 n/n (미충족 항목과 이유)
- 질문: 가정 n · 열린 질문 n · 새로 남김 n
- 남은 작업·결정 필요: (있으면)
```
