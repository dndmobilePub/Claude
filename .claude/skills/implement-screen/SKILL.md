# 화면 구현 절차

> 규칙 원본: `docs/DESIGN.md`, `docs/ARCHITECTURE.md`, `.claude/rules/` (figma-design-system · a11y · finance-ui).
> 이 스킬은 규칙을 반복하지 않고 **작업 순서와 멈춤 지점**만 정한다.

## 입력
- 화면 ID (예: ACC-010). 한 번 실행에 화면 하나만 다룬다.

## 멈춤 조건 (해당하면 즉시 멈추고 묻는다)
- 화면 명세 파일이 없거나 Figma 노드 URL이 비어 있음
- 화면 상태가 "확정"이 아님 (`write-screen-spec`의 확정 점검을 먼저 안내)
- 이 작업에 필요한 `docs/PROJECT.md` 값(스택·라이브러리·스타일링·토큰 위치·명령어)이 [TODO]
- 이 작업에 필요한 `docs/ARCHITECTURE.md` 10번 예외 값(라우트 위치 등)이 [TODO]
- 화면 명세 frontmatter의 `route`가 비어 있음 (라우트를 만드는 화면만)
- Figma 값에 대응하는 토큰·컴포넌트가 없음 (DESIGN.md 8번 절차)
- 필요한 상태(로딩·빈 값·에러 등)의 디자인이 Figma에 없음

## 단계

### 1. 사전 점검
- `docs/screens/<화면ID>.md`를 읽는다. 연결된 플로우 문서는 해당 섹션만 읽는다.
- 다른 화면 명세는 읽지 않는다. (토큰 절감)
- `docs/ARCHITECTURE.md`는 이 화면에 필요한 섹션만 읽는다. (보통 2~6번)
- 같은 도메인의 기존 화면 폴더(`screens/<도메인>/`)와 데이터 계층(`api/<도메인>`)이 있는지 확인한다. 있으면 그 방식을 따른다.
- 멈춤 조건을 확인한다.

### 2. Figma 조회
- `figma-design-system.md` 1번 절차대로 명세의 노드만 조회한다.
- 필요할 때만 `get_variable_defs`, `get_code_connect_map`을 추가로 호출한다.

### 3. 구현 계획 제시 → 승인
아래 내용을 보여주고 승인을 받기 전에는 파일을 만들거나 고치지 않는다.
- 요소 매핑표

  | Figma 요소 | 사용할 컴포넌트 | 구분 (기존 / 확장 / 신규) |
  |---|---|---|

- 대응 토큰이 없는 값 목록
- 만들거나 고칠 파일 목록 (`ARCHITECTURE.md` 2·3번 경로 기준: 화면 폴더, 라우트, 데이터 함수·타입, 임시 데이터, 상태)
- 구현할 상태 목록과 "디자인 필요" 항목
- 아직 정해지지 않은 데이터(API 필드 등)와 임시 처리 방법

### 4. 신규 컴포넌트 (필요할 때만)
- `templates/component-spec.md`로 명세를 먼저 쓰고 승인받은 뒤 만든다.

### 5. 구현
- 승인된 계획 범위 안에서만 작업한다. 범위가 바뀌면 다시 승인받는다.
- 화면 파일은 조립만 하고 디자인 값을 직접 쓰지 않는다.
- 명세에 적힌 상태를 모두 구현한다.
- 화면은 데이터 계층 함수만 호출한다. (`ARCHITECTURE.md` 5번)
- API가 정해지지 않았으면 타입을 먼저 정의하고, 임시 데이터는 데이터 계층 함수 안에서만 반환한다. 임시 처리한 함수에 `TODO(<화면ID>)` 주석을 남긴다. (`ARCHITECTURE.md` 6번)

### 6. 검증
1. `docs/PROJECT.md`의 린트/테스트 명령을 실행한다.
2. `ds-check` 스킬로 디자인 시스템 위반을 점검한다.
3. `get_screenshot`으로 Figma와 비교한다.
4. 상태별로 화면을 확인한다.
5. 규모가 크거나 신규 컴포넌트가 있으면 `design-system-reviewer` 에이전트에 독립 검토를 맡긴다. 화면 ID, 바뀐 파일 목록, ds-check 결과를 함께 넘긴다.
- 위반·차이가 있으면 고친 뒤 다시 검증한다.

### 7. 완료 기준 대조
- 화면 명세의 "완료 기준" 체크리스트를 항목별로 확인한다. 확인하지 못한 항목은 이유를 적는다.

### 8. 보고 → 승인 후 마무리
- 아래 형식으로 보고한다.
- 승인을 받은 뒤:
  - 화면 명세 frontmatter의 `status`를 "구현완료"로, `updated`를 오늘 날짜로 바꾼다. 이번에 만든·확장한 컴포넌트 명세의 `status`도 "구현완료"로 바꾼다.
  - `_index.md`는 고치지 않는다. (`build-index` 훅이 자동 갱신)
  - `docs/GIT.md` 규칙대로 작업 브랜치에 커밋한다. 메시지 형식: `feat(<화면ID>): <화면명> 구현`
  - PR 생성을 제안한다. (생성은 승인 후, `.github/pull_request_template.md` 양식)

## 완료 보고 형식
```
## <화면ID> <화면명> 구현 결과
- 만든/고친 파일: 
- 사용 컴포넌트: 기존 n / 확장 n / 신규 n
- 검증: 린트·테스트 [통과/실패] · ds-check [위반 n건] · Figma 비교 [차이 내용]
- 완료 기준: n/n 충족 (미충족 항목과 이유)
- 남은 TODO: (임시 데이터, 디자인 필요 항목 등)
- 결정 필요: (있으면)
```
