# 디자인 시스템 점검 절차

> 기준: `docs/DESIGN.md` 3·4·7번. 토큰 위치·스타일링 방식은 `docs/PROJECT.md`를 따른다.
> 이 스킬은 **찾아서 보고만** 한다. 수정은 보고 후 승인을 받아 진행한다.

## 점검 범위
- 기본: 현재 작업에서 바뀐 파일만 (`git diff --name-only` + 새 파일)
- 경로를 지정받으면 그 경로만. 전체 점검은 요청받았을 때만 한다. (토큰 절감)
- 제외: 토큰 정의 파일(PROJECT.md의 "코드 토큰 위치"), 테스트·스토리 파일의 목업 데이터, 서드파티 코드

## 점검 항목

### A. 하드코딩 값 (심각도: 높음)
| 항목 | 찾는 패턴 (예시) |
|---|---|
| 색상 | `#fff`, `#1A2B3C`, `rgb(`, `rgba(`, `hsl(` |
| 간격·크기 | 스타일 속성의 `숫자px`, `숫자rem` (margin, padding, gap, width, height 등) |
| 폰트 | `font-size`, `font-weight`, `line-height`, `font-family`에 직접 쓴 값 |
| 반경·그림자 | `border-radius`, `box-shadow`에 직접 쓴 값 |
| 기타 | `z-index`, `opacity`, transition 시간에 직접 쓴 숫자 |
| Tailwind 사용 시 | 임의 값 클래스: `bg-[#...]`, `p-[13px]`, `text-[15px]` 등 |

- 허용: `0`, `auto`, `100%`, `inherit`, `currentColor`, `transparent`, 레이아웃용 `1fr`
- 허용 여부가 애매하면 위반으로 올리지 않고 "확인 필요"로 분류한다.

### B. 스타일 작성 방식 (심각도: 중간)
- 디자인 값을 넣은 인라인 스타일 (`style={{ color: ... }}`)
- 화면(페이지) 파일 안에 직접 쓴 디자인 값 — 화면 파일은 조립만 한다
- `global.css` 예외인데 컴포넌트 변형·공통 스타일로 해결할 수 있는 것, 두 화면 이상에 같은 예외 (`ARCHITECTURE.md` 8-1)
- 의미 토큰이 있는데 원시 토큰을 쓴 경우 (예: `blue.500` 대신 `color.text.link`)
- 용도가 다른 토큰을 빌려 쓴 경우 (예: 에러 색을 경고에 사용)
- 텍스트 스타일 토큰이 있는데 글자 크기·굵기·행간 변수를 하나씩 조합해 쓴 경우 (`DESIGN.md` 3-1)

### C. 컴포넌트 (심각도: 중간)
- 기존 컴포넌트와 이름·구조가 비슷한 새 컴포넌트 (복사 후 변형 의심)
- `button`·`input` 등을 공통 컴포넌트 대신 직접 스타일링한 경우
- 연결 목록(`docs/components/_index.md`, 원본은 명세 `figma_name`)에 있는 Figma 컴포넌트를 다른 코드로 구현한 경우. Code Connect를 쓰면 매핑도 대조한다
- Figma 컴포넌트명과 코드 컴포넌트명이 다른 경우

## 단계
0. 먼저 점검 스크립트를 실행한다: `node .claude/scripts/check-pub.mjs` (지정 경로가 있으면 뒤에 붙인다)
   - 규칙으로 확실히 잡히는 것(P1 정의 안 된 토큰, P2 텍스트 스타일 조합, P3 화면 폭, P4 개발 몫 코드 의심, P5 이동 대상 ID, P6 위험한 HTML·외부 스크립트, P7 스타일 위치)을 찾는다.
   - 결과 표를 그대로 보고에 넣는다. "확인 필요"는 파일을 열어 판단한다. 아래 단계에서 같은 것을 다시 찾지 않는다.
1. 점검 범위를 정하고 대상 파일 목록을 확인한다.
2. A 항목: 패턴 검색(Grep)으로 후보를 찾고, 각 후보를 열어 실제 위반인지 확인한다.
3. 위반 값마다 대응하는 토큰을 토큰 파일에서 찾아 권장 수정을 적는다. 없으면 "대응 토큰 없음"으로 표시한다.
4. B 항목: 대상 파일을 읽어 확인한다.
5. C 항목: 새로 생긴 컴포넌트를 기존 컴포넌트 폴더와 비교한다.
6. 결과를 아래 형식으로 보고한다.

## 결과 보고 형식
```
## ds-check 결과 (범위: <바뀐 파일 n개 / 지정 경로>)
- check-pub: 높음 n · 중간 n · 확인 필요 n (표는 아래에 그대로)
- 위반: 높음 n · 중간 n / 확인 필요 n
```
| 심각도 | 파일:줄 | 위반 내용 | 권장 수정 |
|---|---|---|---|

| 중간 | src/.../Page.tsx:10 | 인라인 스타일로 여백 지정 | 공통 레이아웃 컴포넌트 사용 |

- 대응 토큰 없음: (목록 — DESIGN.md 8번 절차로 결정 필요)
- 확인 필요: (목록과 이유)
- 위반이 없으면 "위반 없음"과 점검한 파일 수만 보고한다.
