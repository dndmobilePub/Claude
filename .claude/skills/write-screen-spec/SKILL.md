# 화면 명세 작성 절차

> 양식: `templates/screen-spec.md`. 기준: `docs/DESIGN.md`, `.claude/rules/finance-ui.md`, `.claude/rules/a11y.md`.
> 질문 기록 규칙: `docs/questions/_index.md` (어느 파일에, 어떤 칸으로, 가정·확정 처리)
> 이 명세는 `implement-screen` 스킬과 `design-system-reviewer`가 그대로 기준으로 쓴다.

## 입력
- 화면 ID (예: TRF-010). 한 번에 화면 하나만 작성한다.
- 모드: 작성(기본) / 확정 점검 (예: `/write-screen-spec TRF-010 확정점검`)

## 원칙
- IMPORTANT: 업무 규칙·문구·데이터를 지어내지 않는다. 자료에 없으면 질문하고, 답이 없으면 `docs/questions/`에 대상 = 이 화면 ID로 남긴다. 명세 본문에는 질문을 적지 않는다.
- 값(색·간격)은 적지 않는다. 컴포넌트·토큰은 이름만 적는다.
- 같은 하위 흐름의 화면을 이어서 작성하면, 앞 화면과 공통인 내용(데이터·금융 규칙)은 다시 묻지 않고 확인만 받는다.
- 파일 저장 전에 전체 초안을 보여주고 승인받는다.

## 작성 모드

### 1. 사전 확인
- `docs/ui-flow/_index.md` 현황에서 화면 ID 행만 검색해 등록 여부를 확인한다. 없으면 `write-flow`로 먼저 등록하도록 안내하고 멈춘다.
- 화면명은 IA 사본(`docs/ia/screen-list.md`)에서 이 화면 ID 행만 검색해 그대로 쓴다. IA가 없는 프로젝트는 플로우 문서 "화면 목록" 표의 이름을 쓴다.
- 연결된 플로우 문서에서 이 화면이 속한 하위 흐름 섹션만 읽는다.
- 명세 파일이 이미 있으면 새로 만들지 않고 수정으로 진행한다.
- `docs/storyboard/<도메인>.md`가 있으면 이 화면 ID의 절만 검색해 읽는다. 다른 화면 절은 읽지 않는다.
- `docs/questions/`에서 이 화면 ID가 대상인 줄만 검색한다. 확정된 답은 명세에 반영돼 있는지 확인하고, 열린 질문은 4단계에서 다시 묻는다.
- 기획서 분석 내용과 플로우·명세가 다르면 임의로 맞추지 않고 질문으로 남긴다. (`spec.md`)

### 2. Figma 확인
- Figma 노드 URL이 있으면 `get_metadata`와 `get_screenshot`으로 화면 구성·상태 프레임만 확인한다. 세부 스타일은 조회하지 않는다.
- 없으면 frontmatter의 `figma`를 비워 두고 "Figma 노드 필요" 질문을 남긴다. (`design.md`, 차단 "예")

### 3. 섹션별 초안
| 섹션 | 채우는 방법 |
|---|---|
| 1. 목적·진입 | 플로우의 하위 흐름에서 가져온다 |
| 2. 구성 | Figma 레이어 순서대로 적고, `docs/components/_index.md`와 코드에서 기존 컴포넌트를 찾아 구분(기존/확장/신규)을 붙인다 |
| 3. 상태 | 6종을 하나씩 확인한다. Figma에 없는 상태는 "디자인 필요" |
| 4. 인터랙션 | 이동 화면이 플로우 문서와 일치하는지 대조한다. 담당은 `ARCHITECTURE.md` 1번 경계로 정하고, 화면 사이 이동은 "개발" |
| 5. 표시 데이터 | 화면에 보이는 값마다 필드 이름과 더미 값을 적는다. API는 알면 개발 참고로, 모르면 "미정" |
| 6. 입력 검증 | 필드별 규칙과 에러 문구. 문구가 없으면 질문 (퍼블은 에러 표시까지, 검증 실행은 개발) |
| 7. 금융 규칙 | `finance-ui.md` 항목 중 이 화면에 해당하는 것만 구체적으로 |
| 8. 접근성 | 화면 제목, 포커스 이동, 특이사항만 |
| 9. 완료 기준 | 공통 항목 유지 + 이 화면 고유 기준 추가 |

### 4. 질문
- 빈칸과 불확실한 항목을 목록으로 모아 한 번에 묻는다. 섹션 번호를 붙여 어디에 들어갈 답인지 밝힌다.
- 답을 받으면 명세에 반영한다. 이미 질문 파일에 있던 질문이면 그 줄을 "확정"으로 바꾸고 반영 위치를 적는다.
- 답을 받지 못한 항목은 `docs/questions/_index.md` 1번 기준으로 파일을 골라 한 줄씩 남긴다. (확인 대상·차단 여부를 정한다)
- 사용자가 임시 값으로 진행하자고 하면 상태 "가정"으로 남기고, 명세 본문 그 자리에 `가정(Q-ID)`를 붙인다. 차단 "예"인 질문은 가정으로 진행하지 않는다.
- 이 화면의 질문 ID를 명세 10번 "관련 질문 ID"에 적는다.

### 5. 초안 제시 → 승인 → 저장
- 완성된 초안 전체를 보여주고 승인받는다. 새로 남길 질문 줄도 함께 보여준다.
- 승인 후:
  - `docs/screens/<화면ID>.md`로 저장한다. 템플릿 주석은 지운다. 질문 줄은 해당 질문 파일에 추가한다.
  - 상태는 frontmatter의 `status`에만 적는다. (열린 질문이 있으면 "초안", 확인 요청 중이면 "검토") `updated`도 오늘 날짜로 바꾼다.
  - `_index.md`는 고치지 않는다. `build-index` 훅이 자동으로 갱신한다. 훅 경고가 나오면 보고한다.

## 확정 점검 모드
아래를 모두 만족하면 frontmatter `status`를 "확정"으로 바꾸자고 제안한다. (변경은 승인 후, `updated`도 함께 갱신)

- [ ] frontmatter `figma`에 노드 URL이 있다
- [ ] 1~9번 섹션이 채워져 있거나 "해당 없음"으로 표시돼 있다
- [ ] 3번 상태마다 Figma 노드가 있거나, "디자인 필요" 항목에 대해 처리 방법이 정해졌다
- [ ] 4번 이동 화면이 플로우 문서와 일치한다
- [ ] 2번 "신규" 컴포넌트는 명세 작성 계획이 있다
- [ ] 4번 모든 행에 담당(퍼블/개발)이 있다
- [ ] 5번 표시 데이터마다 필드 이름과 더미 값이 있다 (API "미정"은 허용)
- [ ] 대상이 이 화면 ID이고 차단 "예"인 질문이 모두 확정이다 (`docs/questions/`에서 화면 ID로 검색)
- [ ] 확정된 질문의 답이 명세에 반영돼 있다
- [ ] 본문의 `가정(Q-ID)`가 모두 상태 "가정"인 질문을 가리킨다 (확정된 것은 값으로 바뀌어 표시가 없다)

- 통과하지 못한 항목은 무엇이 빠졌는지와 확인 대상을 보고한다.

## 완료 보고 형식
```
## <화면ID> <화면명> 명세 결과
- 파일: docs/screens/<화면ID>.md (상태: 초안/검토/확정)
- 컴포넌트: 기존 n / 확장 n / 신규 n
- 디자인 필요 상태: (목록)
- 질문: 새로 남김 n · 열린 질문 n (차단 n) · 가정 n (ID 목록)
- 다음 작업: (확정 점검 / 컴포넌트 명세 / implement-screen)
```
