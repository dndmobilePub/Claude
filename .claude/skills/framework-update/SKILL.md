# 공통 지침 업데이트 절차

> 분류의 원본은 `.claude/framework.json`의 `files`(교체 / 병합 / 선택 / 설정 / 프로젝트 / 원본 전용)다. 원본 전용(`tests/`)은 비교하지 않는다.
> 비교·반영은 `node .claude/scripts/framework-update.mjs`가 한다. 이 스킬은 순서와 승인 지점을 정한다.

## 멈춤 조건
- 작업 트리에 커밋되지 않은 변경이 있음
- `.claude/framework.json`이 없거나 버전이 비어 있음 (복사해서 시작한 프로젝트 → 어느 버전에서 복사했는지 사용자에게 묻고 그 버전으로 적은 뒤 시작)
- 새 버전이 major로 올라감 (예: v1 → v2) — `CHANGELOG.md`의 "옮기는 방법"을 먼저 함께 읽고 진행 여부를 묻는다

## 단계

### 1. 지금 버전과 새 버전 확인
- 지금 버전: `.claude/framework.json`의 `version`
- 새 버전: `git ls-remote --tags <repository>`로 태그 목록을 보고, 사용자가 고른 버전을 쓴다. 정하지 않았으면 가장 최근 태그를 제안한다.
- 건너뛰는 버전이 있어도 한 번에 올려도 된다. 단 major가 바뀌면 major마다 나눠서 올린다.

### 2. 두 버전 받기
- 저장소 밖 임시 폴더에 두 버전을 받는다. 프로젝트 안에 받지 않는다.
  ```
  git clone --depth 1 --branch v<지금 버전> <repository> <임시 폴더>/from
  git clone --depth 1 --branch v<새 버전> <repository> <임시 폴더>/to
  ```
- 새 버전 `CHANGELOG.md`에서 지금 버전 다음부터 새 버전까지의 항목만 읽는다.

### 3. 비교 보고 → 승인
- `node .claude/scripts/framework-update.mjs check --from <임시 폴더>/from --to <임시 폴더>/to`
- 사용자에게 보여줄 것:
  - CHANGELOG 요약 (바뀐 규칙·스킬)
  - 처리별 개수와 표 (스크립트 출력 그대로)
  - 충돌·설정 확인·위치 확인·선택 확인 파일 목록과 각각 어떻게 할지 제안
  - 프로젝트에서 지운 선택 파일(업종 규칙 등)은 보고에 나오지 않는다. 일부러 뺀 것으로 본다
- 승인 전에는 파일을 고치지 않는다.

### 4. 충돌 정리 (있을 때만)
충돌은 프로젝트가 공통 부분을 직접 고친 파일이다. 파일마다 차이를 보여주고 하나씩 정한다.
- 차이 보기: `git diff --no-index <임시 폴더>/from/<파일> <프로젝트 파일>`
- 고친 내용이 프로젝트 값이면 → 그 문서의 "프로젝트별 예외" 섹션으로 옮기고, 공통 부분은 지금 버전으로 되돌린다. (승인 후)
- 공통으로 필요한 수정이면 → 원본 저장소에 반영을 제안하고, 이 파일은 지금 버전으로 되돌린다.
- 그대로 두기로 정하면 → 5단계에서 `--keep-conflicts`를 붙이고, 보고에 남긴다. 다음 업데이트에서도 충돌로 다시 나온다.

### 5. 반영
- `node .claude/scripts/framework-update.mjs apply --from <임시 폴더>/from --to <임시 폴더>/to` (4단계에서 그대로 두기로 한 충돌이 있으면 `--keep-conflicts`)
- 교체·병합·추가·삭제가 반영되고 `.claude/framework.json`이 새 버전으로 바뀐다.

### 6. 설정 확인·위치 확인
- 설정 확인: 스크립트가 보여준 "지금 버전 → 새 버전" 차이를 프로젝트 파일에 옮길지 줄마다 제안하고 승인받아 고친다.
  - `docs/PROJECT.md`에 새 항목이 생겼으면 값을 묻는다. 모르면 `[TODO]`로 둔다.
  - `.claude/settings.json`은 프로젝트가 바꾼 권한을 지키며 새 줄만 더한다.
  - rules frontmatter는 프로젝트의 `paths` 앞부분(퍼블 소스 폴더)을 지키며 바뀐 부분만 옮긴다.
- 선택 확인: 새 버전에 새로 생긴 선택 파일(업종 규칙 등)이다. 이 프로젝트에 맞는지 사용자에게 묻고, 쓰기로 하면 새 버전 폴더에서 가져와 `docs/PROJECT.md` "업종 규칙"에 적는다. (승인 후)
- 위치 확인: 퍼블 소스 폴더·컴포넌트 폴더가 다른 프로젝트에서 찾지 못한 파일이다. 실제 위치(`docs/ARCHITECTURE.md` 11번)의 파일에 병합 규칙대로 직접 반영한다.

### 7. 점검
- `node .claude/hooks/build-index.mjs` — AUTO 블록을 다시 만들고 경고를 확인한다.
- 새 버전에 새 점검·규칙이 생겼으면 그 영향(예: 새 check-pub 항목)을 `node .claude/scripts/check-pub.mjs <퍼블 소스 폴더>`로 한 번 돌려 보고만 한다. 퍼블 수정은 이 스킬에서 하지 않는다.

### 8. 커밋 (승인 후)
- 브랜치 `chore/framework-v<새 버전>`, 커밋 `chore(framework): v<지금 버전> → v<새 버전> 반영`
- 공통 지침 반영과 프로젝트 문서 수정(예외 섹션 채우기 등)은 커밋을 나눈다. (`docs/GIT.md` 3번)

## 규칙
- IMPORTANT: 스크립트가 고치지 않은 파일(충돌·설정 확인·위치 확인)을 사람 승인 없이 고치지 않는다.
- IMPORTANT: 프로젝트 소유 파일(명세·플로우·질문·보고·`docs/PRODUCT.md`·퍼블 파일)은 이 스킬에서 고치지 않는다.
- 공통 규칙을 프로젝트에서 바꾸고 싶으면 예외 섹션에 적거나 원본 저장소에 제안한다. 공통 부분을 직접 고치면 다음 업데이트에서 충돌이 된다.
- 임시 폴더는 지우지 않아도 된다. (운영체제 임시 폴더에 둔다)

## 완료 보고 형식
- v<지금 버전> → v<새 버전>, CHANGELOG 요약 3줄 이내
- 반영: 교체 n · 병합 n · 추가 n · 삭제 n
- 사람과 정한 것: 충돌 처리, 설정 확인에서 옮긴 줄, `[TODO]`로 남긴 새 항목
- 점검 결과: build-index 경고 n건, check-pub 새 항목 결과
